# ADR-035

标题：V1 Pilot 用反馈闭环决定 V1.1 或继续观察；核心看老板明天还用不用

- 状态：proposed
- 日期：2026-08-17

## 背景

观察表已规定记什么。若反馈不分类、失败不处理、把「功能愿望」当成迭代依据，试班会变成加功能，或过早开工 V1.1。

手册：[V1_SALES_CLERK_PILOT_RUNBOOK.md](../V1_SALES_CLERK_PILOT_RUNBOOK.md)、[ADR-036](ADR-036-v1-pilot-runbook.md)。服从 [ADR-031](ADR-031-v1-pilot-observation.md)、[ADR-034](ADR-034-v1-pilot-onboarding.md)、[RUNTIME_FREEZE.md](../RUNTIME_FREEZE.md)。

## 问题

真实老板试用期间如何收集反馈，并形成能否进入 V1.1 的产品依据？

## 决策

1. 本阶段 **不开发新功能**。不改 Runtime / Confirm Gate，不新增 Agent，不扩展库存/支付/财务。
2. 只验证 AI 是否成为日常开单习惯。不验证替代老板。
3. 每日记：日期、当天订单量、AI 参与数量、人工接管、失败案例。收摊问「明天还用吗」。
4. 反馈分四类：信任 / 理解 / 流程 / 数据。失败模板含原话、理解、结果、分类、处理。
5. 处理只三选一：**补事实**、**优化规则**（冻结外侧）、**暂不处理**。优化规则不是解冻 Confirm Gate。
6. 结束只选：**进入 V1.1 开发** 或 **继续观察**。核心标准：老板是否愿意第二天继续使用。不愿再用则暂停或改流程，不开工 V1.1。

## 原因

没有闭环，观察数字不会变成迭代依据。有分类和处理，才不会用「老板不敢确认」去放宽闸门。

## 影响

- 好处：V1.1 入口可执行；失败有去向。
- 限制：要有观察人；不自动埋点；继续观察不是无限期开发。
