旁边有人记。老板只管喊单，不填满意度问卷。

## 0. 结论

反馈闭环不是加功能的借口，是把试用变成 **可执行的迭代依据**。

```text
每天记用量
  → 失败/抱怨按四类归档
  → 每条失败填模板（原话 / 理解 / 结果 / 分类 / 处理）
  → 处理只三选一：补事实 / 优化规则（冻结外侧）/ 暂不处理
  → 核心问句：老板明天还用不用
  → 进入 V1.1 开发  或  继续观察
```

核心标准：**老板是否愿意第二天继续使用。**  
不是：功能是否变多、AI 是否能替代老板。

观察表的「数据不足 / 产品设计 / Runtime」是 **原因**。本文的四类是 **老板侧表现**。两者要对上，不能各记一套。

---

## 1. Pilot 目标

验证：

**AI 是否成为老板日常开单习惯。**

现场怎么看：第二天还打开今日本、还愿意喊下一单、收摊还扫本子，而不是把同一张单写回纸本/微信。

| 验证 | 不验证 |
| --- | --- |
| 少手写、少问「写了没」、少翻聊天（观察表 §1） | **AI 是否替代老板**（货、价、放不放货仍是老板的） |
| 第二天还用 | 无人值守、功能很多、听懂全部档口话 |
| 失败能闭环（补事实或记下资产） | 用反馈当理由改 Confirm Gate、加库存/支付/财务 |

成功时老板会说：**「明天还用，少记单。」**  
失败时老板会说：不敢点好了、还是手写快、这 AI 功能很多。

## 2. 每日反馈记录

一天一张。观察人填，不发给老板填。数字能和今日本对上。

**档口：** ________　**观察人：** ________　**有人盯：** 是 / 否

| 项 | 记法 | 当天 |
| --- | --- | --- |
| **日期** | 营业日 | ________ |
| **老板当天订单量** | 当天实际开出的单（含仍手写/微信的） | ________ |
| **AI 参与订单数量** | 今日本上走到「好了」的单 | ________ |
| **人工接管次数** | 观察人代点、改口令、解释状态、老板因听错而重喊 | ________ |
| **失败案例** | 编号列表，每条另开模板 | ________ |

当天收摊只问一句（记原话）：

> 明天还用这个开单吗？

| 答 | 怎么用 |
| --- | --- |
| 用 / 还开 | 习惯在形成；继续记 |
| 不一定 / 看情况 | **继续观察**，不要当天宣布 V1.1 |
| 不用了 / 还是手写 | 不进入 V1.1；对照四类找主因 |

与观察表同一天只填一份现场表：订单量 = 观察表「订单数量」的超集（含手写）；AI 参与 = 观察表「成功开单数量」。不要两套对不上的账。

## 3. 用户反馈分类

先看老板 **感觉到什么**，再对到原因和处理。一类一条主标签，不要「全都有」。

### 3.1 信任问题

老板不敢把单交给这个伙计。

例如：不敢说「好了」；说了还抄纸本；不看今日本；怕写错客。

| 对上原因 | 处理倾向 |
| --- | --- |
| 当前单不清、确认含义不明 | 产品流程 → 改呈现/话术，不改闸门 |
| 入账状态看不懂 | 产品流程（投影文案） |
| 同名曾写错过 | 数据或理解；先保证问、禁止猜 |

不敢确认 **不是** 要放宽 Confirm Gate。闸门在，才敢用。

### 3.2 理解问题

商品或客户识别错了。

例如：李老板写成王老板；苹果听成梨；改口变两行；该问规格却落到某个 SKU。

| 对上原因 | 处理倾向 |
| --- | --- |
| 目录里有、规则问了却猜 | Runtime（先记案例，改代码须另批且不破 Freeze） |
| 口语不在树上/别名 | 数据缺失 → 补事实；原话进语言资产 |
| Demo 映射让人以为任意口语都行 | 产品流程 |

### 3.3 流程问题

操作比手写慢，或不知道下一手做什么。

例如：不知要「再开一单」；复述当成已经好了；高峰时按住说话不如抄纸；换页要观察人提醒。

处理倾向：冻结 **外侧**（今日本、话术、试班纪律）。不新增 Agent，不加表单加行当主操作。

### 3.4 数据问题

缺客户、缺 SKU。

例如：张老板不在目录；苹果没有可确认叶；同名没有档口。

处理倾向：**补事实**（人补来源 → Adapter 再投影）。不自动建档、不自动建 SKU。询问/挂起是正确行为，不要当成理解 bug。

## 4. 每个失败案例记录模板

每一个失败单独一条。原话尽量原样。**禁止**写进 Memory。

```text
案例编号：F-YYYYMMDD-__
日期 / 档口：
老板原话（输入）：
AI 理解（口播 + 当前区实际）：
实际结果（本子上最后是什么）：
最终正确结果（人认定该是什么）：

用户侧分类（只勾一个）：
[ ] 信任问题     不敢确认 / 回退手写 / 不看本
[ ] 理解问题     客户或商品认错
[ ] 流程问题     比手写慢 / 不会换页 / 把复述当好了
[ ] 数据问题     缺客户 / 缺 SKU / 消歧事实不够

原因（与观察表一致，只勾一个）：
[ ] 数据缺失
[ ] 理解错误（含 Runtime 与设计不符）
[ ] 产品流程

处理（只选一个）：
[ ] 补事实      人把客/货/档口补进来源再投影
[ ] 优化规则    冻结外侧：今日本文案、试班话术、语言资产、关 Demo 映射
[ ] 暂不处理    样本不足；只沉淀口语，不改产品、不改闸门

下一步：
明天还用？是 / 否 / 未问
```

处理规矩：

| 选择 | 可以做什么 | 不可以做什么 |
| --- | --- | --- |
| **补事实** | 补 Catalog 切片 | 让 AI 建客户/SKU；聊天进 Memory |
| **优化规则** | 工作台更清楚、话术、金脚本纪律 | 改 Confirm Gate、改 Parser 迁就一句口语、新 Agent |
| **暂不处理** | 记入语言资产，等同类案例 | 用「先修一刀」改内核；用反馈上库存/支付/财务 |

「优化规则」**不是**解冻 Runtime。闸门与确认语义不动。若案例显示闸门被绕过，记 Runtime 原因，先对照检查清单，不在本闭环里改代码。

## 5. Pilot 结束判断

试满约定天数（建议至少 **3 个早市**，含 1 次高峰）后，看反馈表，只选一个方向。

核心标准：

**老板是否愿意第二天继续使用。**

### 进入 V1.1 开发

同时满足：

1. 多数天回答「明天还用」。
2. AI 参与订单数量稳定大于 0，且明显多于纯手写回退。
3. 失败以 **数据问题** 为主，处理是补事实；或少量流程/信任问题，处理是冻结外侧打磨。
4. 没有靠猜同名、确认后改单、ERP 挡「好了」才换来「明天还用」。
5. 检查清单五项仍通过。

V1.1 只做冻结外侧：今日本更清楚、试班纪律、语言资产、可选真实模式（关 Demo 映射）。**不**加收款、库存、第二员工，**不**改 Confirm Gate。与观察表「继续 V1.1」同一扇门。

### 继续观察

出现任一条，先不要开工 V1.1：

1. 「明天还用」只有一天，或高峰日没问到。
2. AI 参与有，但人工接管几乎每张都要，还分不清是数据还是流程。
3. 失败案例不足（同类少于 3 条）就想改规则。
4. 老板说还用，但收摊仍只翻聊天——习惯未稳，再记几天。

继续观察 = 还按本闭环记账，不扩功能。不是无限期试下去当开发。

若多数天 **不愿意** 第二天再用：不要进入 V1.1，也不要用「再观察一周」掩盖。回到接入的 **暂停**，或观察表的 **调整产品流程**（先改旅程/工作台，不加功能）。

---

## 6. 反馈如何变成产品迭代依据（收口）

```text
明天还用？
  多数天：是  +  失败能补事实或外侧打磨  →  进入 V1.1 开发
  是，但样本不够 / 高峰未见            →  继续观察
  多数天：否                           →  暂停或改流程（不开工 V1.1，不加库存支付）
```

迭代依据是 **分类后的失败模板 + 明天还用**，不是功能愿望清单。

## 评审六问

1. **哪一层？** Pilot 反馈闭环（记录与决策）。不改内核。
2. **改 LLM 权限？** 否。
3. **改 Confirm Gate？** 否。不敢确认不靠放宽闸门解决。
4. **污染 Memory？** 否。原话只进本模板 / 语言资产。
5. **经 Event？** 否。本文只记录。确认事件仍只来自「好了」。
6. **Adapter 还是 Runtime？** 都不在本阶段改。补事实走已有投影路径。
